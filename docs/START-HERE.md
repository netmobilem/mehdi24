# 🚀 از صفر تا کانفیگ تست‌شده — راهنمای گام‌به‌گام

این سند دقیقاً همان مسیری است که باید طی کنید: **آپلود روی گیت‌هاب → اجرا روی Railway → آماده‌سازی نود → ساخت کانفیگ → تست**. هر مرحله یک «چک» دارد که با آن مطمئن می‌شوید درست پیش رفته‌اید.

---

## مرحله ۰ — آماده‌سازی فایل‌ها

در پوشه‌ی پروژه:

```bash
bash scripts/package.sh          # می‌سازد: dist/titan-panel-1.0.0.zip
unzip dist/titan-panel-1.0.0.zip
cd titan-panel-1.0.0
```

> چه چیزی داخل آرشیو است: کد پنل، ایجنت نود، استاتیک، Dockerfile، railway.json، docker-compose، اسکریپت نصب VPS، تست‌ها و مستندات.
> چه چیزی **نیست**: دیتابیس محلی، کش‌ها، کلیدها و فایل `.env` (امنیت).

## مرحله ۱ — آپلود روی گیت‌هاب

**راه الف) با گیت (پیشنهادی)**

```bash
git init
git add .
git commit -m "TiTaN Panel v1.0.0"
git branch -M main
git remote add origin https://github.com/<username>/titan-panel.git   # ریپو را از قبل ساخته باشید (Private هم اشکالی ندارد)
git push -u origin main
```

**راه ب) بدون گیت:** در گیت‌هاب روی **Add file → Upload files** بزنید و محتویات پوشه را بکشید و رها کنید.

✅ **چک:** در گیت‌هاب باید این‌ها را ببینید: `Dockerfile`, `railway.json`, `requirements.txt`, پوشه‌های `app/`, `agent/`, `static/`.

## مرحله ۲ — اجرا روی Railway

1. وارد [railway.app](https://railway.app) شوید → **New Project** → **Deploy from GitHub repo** → ریپوی `titan-panel` را انتخاب کنید.
2. Railway فایل `Dockerfile` را خودش پیدا و بیلد می‌کند (چون `railway.json` هست، healthcheck روی `/healthz` تنظیم می‌شود).
3. **متغیرهای محیطی** — سرویس → تب **Variables**:

   | متغیر | مقدار | چرا |
   |---|---|---|
   | `ADMIN_PASSWORD` | یک رمز قوی | رمز ورود ادمین (اگر نگذارید `admin` می‌شود) |
   | `SECRET_KEY` | یک رشته‌ی تصادفی ۴۰+ کاراکتری | ثابت ماندن نشست‌ها |
   | `PORT` | دست نزنید (یا `8080`) | Railway خودش می‌دهد؛ اگر خودتان بدهید همان مقدار برای اپ و دامنه استفاده می‌شود |
   | `EXTRA_PORTS` | `8080,8000,3000` (پیش‌فرض) | پنل علاوه بر `PORT` روی این پورت‌ها هم گوش می‌دهد تا پورت هدف دامنه هیچ‌وقت اشتباه نشود |
   | `DATA_DIR_FALLBACK` | `/tmp/titan-data` (پیش‌فرض) | اگر ولوم `/data` قابل‌نوشتن نبود، دیتابیس موقتاً اینجا ساخته می‌شود (پنل بالا می‌آید ولی داده پایدار نیست) |

4. **Volume (خیلی مهم)** — سرویس → **Volumes** → **New Volume** → مسیر مانت: **`/data`**.
   بدون این کار، با هر دیپلوی همه‌ی کاربران و کانفیگ‌ها پاک می‌شوند.
5. **دامنه‌ی عمومی** — سرویس → **Settings → Networking → Generate Domain** تا `RAILWAY_PUBLIC_DOMAIN` پر شود (لینک‌های اشتراک از همین دامنه ساخته می‌شوند).

✅ **چک:** `https://<your-app>.up.railway.app/healthz` باید JSON با `"ok": true` برگرداند. اگر ۵۰۲ بود، لاگ‌های Deploy را ببینید (معمولاً رمز/پورت یا خطای نصب وابستگی).

### 🚨 اگر خطای «Application failed to respond» دیدید

این خطا یعنی **ادج Railway به اپ وصل نشده** (۵۰۲) و ۹۹٪ مواقع علتش **پورت** است: پورت هدفِ دامنه با پورتی که اپ گوش می‌دهد یکی نیست.
در نسخه‌ی فعلی پنل هم‌زمان روی `PORT` و `8080` (و روی IPv4 و IPv6) گوش می‌دهد، پس:

1. Railway → سرویس → **Deployments → آخرین دیپلوی → View Logs**. دنبال این خط بگردید:
   ```
   TiTaN is listening on: 0.0.0.0:8080  [::]:8080  0.0.0.0:8000  [::]:8000
   ```
   همین خط می‌گوید اپ روی چه پورت‌هایی بالاست (معمولاً `8080` چون Railway خودش `PORT=8080` می‌دهد).
2. Railway → سرویس → **Settings → Networking** → روی دامنه کلیک کنید → **Target Port** را برابر یکی از همان پورت‌ها بگذارید (معمولاً `8080`) → ذخیره.
   ⚠️ این مقدار جادویی نیست: **پورت هدف دامنه، متغیر `PORT` داخل اپ را عوض نمی‌کند** — باید با آن یکی باشد.
3. اگر می‌خواهید پورت ثابت و قابل پیش‌بینی باشد: تب **Variables** → `PORT=8080` را خودتان تعریف کنید (Railway هم همان را می‌دهد) و پورت هدف دامنه را هم `8080` بگذارید → **Redeploy**.
4. چک نهایی: `https://<app>.up.railway.app/healthz` → در پاسخ، فیلد `listen` پورت‌های فعال را نشان می‌دهد:
   ```json
   {"ok": true, "listen": ["0.0.0.0:8080", "[::]:8080", "0.0.0.0:8000", "[::]:8000"]}
   ```
5. اگر باز هم ۵۰۲ بود، **لاگ ابزار دپلوی خود را عوض کنید**: صبر کنید لاگ کامل بالا بیاید و ۲۰ خط آخر را بفرستید؛ اگر خط
   `no port could be bound` یا `cannot listen on` دیدید، یعنی پورت اشغال است و باید `PORT`/`EXTRA_PORTS` را عوض کنید.

> نکته: اگر لازم شد پورت‌های بیشتری هم گوش دهند: `EXTRA_PORTS=8080,3000,8000` (با کاما). برای خاموش کردن این قابلیت: `EXTRA_PORTS=`.

### 🟢 اگر وضعیت دیپلوی «Completed» شد (به رنگ سبز) و آنلاین نشد

در Railway معنی **Completed** این است: **پروسه‌ی اپ با کد خروج صفر تمام شده** (یعنی «کارش را کرد و تمام»، نه کرش).
این حالت تقریباً همیشه یعنی راه‌اندازی اپ وسط کار خطا خورده و uvicorn (مثل هر وب‌سرور دیگر) با کد ۰ بیرون آمده. شایع‌ترین علت روی Railway:
**ولوم `/data` قابل‌نوشتن نبوده** (مالکیت root) یا فایل دیتابیس باز نشده.

| قدم | کار |
|---|---|
| ۱ | **Deploy Logs** را باز کنید و دنبال `Application startup failed. Exiting.` و بالای آن `Traceback` بگردید — خط آخر دقیقاً می‌گوید چه چیزی کم بود (مثلاً `PermissionError: /data` یا `sqlite3.OperationalError: unable to open database file`). |
| ۲ | از نسخه‌ی **۱.۰.۲** به بعد این حالت **دیگر اپ را نمی‌بندد**: اگر `/data` قابل‌نوشتن نباشد، خودش به `DATA_DIR_FALLBACK` (پیش‌فرض `/tmp/titan-data`) سوییچ می‌کند، هشدار بزرگ در لاگ می‌دهد و به سرویس‌دهی ادامه می‌دهد. اگر حتی آن هم نشد، با **کد خروج ۱** و تریس‌بک کامل می‌بندد (یعنی «Crashed» با لاگ روشن، نه Completed). |
| ۳ | راه‌حل دائمی برای پایداری داده: Railway → **Volumes → New Volume → Mount path: `/data`** و سپس **Redeploy**. ایمیج خودش مالکیت `/data` را در استارت به کاربر `titan` می‌دهد (`[entrypoint] ...` در لاگ). |
| ۴ | «Completed» یعنی Railway ری‌استارت نمی‌کند (با `ON_FAILURE`). در نسخه‌ی ۱.۰.۲ فایل `railway.json` روی **`restartPolicyType: ALWAYS`** تنظیم شده تا اگر پروسه به هر دلیلی تمام شد، سرویس خودش دوباره بالا بیاید. |
| ۵ | اگر در **Settings → Deploy** خودتان یک مقدار برای **Custom Start Command** یا **Healthcheck Path** گذاشته‌اید، پاکشان کنید تا مقدارهای خود پروژه (`railway.json` + Dockerfile) اعمال شود. |

> بعد از هر دیپلوی، همیشه همین خط را در لاگ ببینید: `TiTaN is listening on: …` — اگر این خط نبود، اپ بالا نیامده و بقیه‌ی بحث پورت بی‌فایده است.

6. وارد `https://<your-app>.up.railway.app` شوید و با `admin` / رمزی که گذاشتید وارد شوید.
   → **تنظیمات → تغییر رمز** را همان‌جا انجام دهید.

## مرحله ۳ — آماده‌سازی نود (سرور پروکسی)

نود همان جایی است که Xray و Nginx اجرا می‌شوند؛ پس **بهترین کیفیت با یک VPS خام** به دست می‌آید (نه کانتینر).

**۱) پیش‌نیازها روی VPS:**

- یک VPS با Ubuntu 22.04/24.04 یا Debian 12 (۱ vCPU / ۱GB RAM برای شروع کافی است)
- یک **دامنه یا زیردامنه** که A-Record آن به آی‌پی سرور اشاره کند (مثل `de.titan.example.com`) — برای TLS لازم است
  - بدون دامنه هم می‌توانید کار کنید: کانفیگ را با امنیت **REALITY** بسازید (بدون گواهی کار می‌کند)
- رمز root یا کلید SSH

**۲) افزودن سرور در پنل:** **سرورها (Node ها) → افزودن سرور** و پر کردن:

- نام، آدرس (همان دامنه)، پورت عمومی `443`، پورت ایجنت (پیش‌فرض `62050`)
- کشور و شهر (فقط برای نمایش و مرتب‌سازی؛ کد کشور دو حرفی مثل `DE`)
- اطلاعات SSH (هاست، پورت، کاربر، رمز)

**۳) دکمه‌ی «نصب خودکار»** را بزنید. با SSH وارد سرور می‌شود و:

- `nginx` (کامل، با ماژول stream) و **Xray-core** رسمی را نصب می‌کند
- کرنل را تیون می‌کند (`BBR`, `fq`, `TCP Fast Open`, بافرها)
- فایروال را تنظیم می‌کند (۲۲/۸۰/۴۴۳ + پورت اختصاصی کانفیگ‌های direct + پورت ایجنت)
- ایجنت TiTaN را به‌عنوان سرویس systemd بالا می‌آورد و سلامت آن را چک می‌کند

اگر SSH مستقیم ندارید: در صفحه‌ی جزئیات سرور، **اسکریپت دستی نصب** را دانلود و روی سرور اجرا کنید:

```bash
bash titan-bootstrap-1.sh
```

✅ **چک:** در صفحه‌ی سرورها، کارت سرور **سبز = آنلاین** شود و CPU/RAM/پینگ زنده نمایش داده شود.
اگر آفلاین ماند → بخش «عیب‌یابی» پایین همین سند.

**۴) صدور گواهی TLS:** در صفحه‌ی جزئیات سرور → **صدور/تمدید گواهی TLS** → دامنه را تأیید کنید.
(دامنه باید به همین سرور اشاره کند و پورت ۸۰ باز باشد.)

## مرحله ۴ — ساخت اولین کانفیگ و کاربر

1. **کانفیگ‌ها → کانفیگ جدید**:
   - سرور: همان نود
   - پروتکل `VLESS` · ترابری `XHTTP` (پیشنهاد مدرن؛ برای شروع سبک `WS` هم عالی است) · امنیت `TLS`
   - پورت `443` · مسیر: خالی بگذارید (خودکار) · ALPN: `h2,http/1.1` · Fingerprint: `chrome`
   - تیک «همه‌ی کاربران فعلی وصل شوند» را بزنید اگر از قبل کاربر دارید
2. اگر به‌جای آن سرور دامنه‌ی معتبری ندارد: امنیت را `REALITY` بگذارید — کلیدها همان لحظه ساخته می‌شوند.
3. روی ردیف کانفیگ دکمه‌ی **استقرار (↓ روی نود)** را بزنید.
   پنل با `xray -test` و `nginx -t` اعتبارسنجی می‌کند و بعد ری‌استارت — اگر چیزی خراب باشد **کانفیگ قبلی برمی‌گردد** و در «گزارش‌ها» ثبت می‌شود.
4. **کاربران → کاربر جدید**: نام کاربری، سرور، حجم (مثلاً ۱۰ GB)، حد دستگاه `2`، مدت اعتبار `30` روز.
5. در لیست کاربران، آیکون **لینک‌ها** → لینک `vless://…` و **QR** را ببینید. لینک `sub/…` را در v2rayNG اضافه کنید تا همه‌ی کانفیگ‌ها خودکار بیایند.
6. **اشتراک‌ها → گروه اشتراک جدید** برای ساخت یک لینک حرفه‌ای با صفحه‌ی عمومی (`/s/<token>`).

✅ **چک نهایی:** با کلاینت موبایل QR را اسکن کنید → اتصال برقرار شود → در پنل، داشبورد کارت «کاربران آنلاین» و «ترافیک مصرفی» عدد بگیرد و در صفحه‌ی کاربر `used` بالا برود. یعنی چرخه‌ی کامل (کانفیگ → اتصال → آمار) کار می‌کند.

> آمار هر ۱۵ ثانیه یک‌بار از نود خوانده می‌شود؛ ممکن است تا نیم دقیقه بعد از اتصال، در پنل عدد ببینید.

## 🧯 عیب‌یابی سریع

| نشانه | علت احتمالی | راه‌حل |
|---|---|---|
| سرور **آفلاین** می‌ماند | ایجنت نصب/بالا نیامده یا پورت ایجنت در فایروال بسته است | روی سرور: `systemctl status titan-agent` و `ss -lntp \| grep 62050` — در پنل روی «تست SSH» بزنید |
| در پنل `Connection refused` روی ایجنت | فایروال ارائه‌دهنده بیرونی (Security Group) پورت ایجنت را بسته | پورت ایجنت را در پنل ابری سرور باز کنید یا فقط به آی‌پی Railway اجازه دهید |
| «صدور گواهی ناموفق» | دامنه به سرور اشاره نمی‌کند / پورت ۸۰ بسته است / Let's Encrypt rate-limit | `dig +short <domain>` را چک کنید؛ `ufw status`؛ یا از REALITY استفاده کنید |
| `xray -test` رد می‌شود | کانفیگ بدون گواهی ولی با امنیت TLS | اول گواهی صادر کنید یا امنیت را REALITY کنید |
| استقرار می‌گوید «تداخل پورت ۴۴۳» | کانفیگ `direct` (TCP/QUIC) روی پورت nginx | پورت اختصاصی بدهید (مثلاً ۸۴۴۳) — پنل خودش هم پیشنهاد می‌دهد |
| اتصال وصل می‌شود ولی ترافیک رد نمی‌شود | دامنه/SNI یا path با کلاینت هم‌خوان نیست | در صفحه‌ی لینک‌های کاربر، لینک دقیق و JSON کلاینت را کپی کنید (host/sni/path/alpn همان‌جاست) |
| وضعیت دیپلوی **Completed** (سبز) و سرویس آنلاین نمی‌شود | راه‌اندازی اپ خطا خورده (اغلب ولوم `/data` قابل‌نوشتن نبوده) و uvicorn با کد ۰ بیرون آمده | از ۱.۰.۲ به بعد خودکار فالبک می‌کند؛ تریس‌بک `Deploy Logs` را ببینید و ولوم را روی `/data` وصل کنید — بخش «Completed» بالا |
| Railway بالا می‌آید ولی «Application failed to respond» می‌دهد | **پورت هدف دامنه ≠ پورتی که اپ روی آن گوش می‌دهد** | لاگ Deploy را ببینید (خط `TiTaN is listening on:`)، بعد Settings → Networking → Target Port را `8080` بگذارید، یا `EXTRA_PORTS` را تنظیم کنید — جزئیات در بخش بالا |
| بعد از دیپلوی همه چیز پاک شده | Volume وصل نشده | Railway → Volumes → سرویس را به `/data` وصل کنید |
| پنل کند شده | آمار زیاد یا نودهای زیاد | بازه‌ی پاک‌سازی در `app/workers.py` قابل تنظیم است؛ برای مقیاس بزرگ به Postgres مهاجرت کنید |

لاگ‌ها: پنل → **گزارش‌ها** (رخدادها) · سرور → دکمه‌ی **دریافت لاگ‌های زنده** · روی VPS: `journalctl -u titan-agent -f` و `journalctl -u xray -n 50`.
