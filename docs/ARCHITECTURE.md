# معماری TiTaN Panel

این سند تصمیم‌های مهندسی و دلیل‌شان را توضیح می‌دهد: چرا هسته ترکیبی، چرا ایجنت، چرا این مدل داده، و هر چیزی که برای نگهداری بلندمدت لازم است.

---

## ۱) تصویر کلی

```
┌─────────────────────────── پنل (کنترل‌پلین) ───────────────────────────┐
│  FastAPI + Jinja (SSR) + SQLite(WAL)                                  │
│                                                                       │
│  routers/  ── صفحات و اکشن‌ها (HTML + AJAX)                            │
│  services/ ── منطق دامنه: کانفیگ‌ساز، استقرار، حسابداری، لینک، امنیت     │
│  workers/  ── ۵ حلقه‌ی async: سلامت · آمار · محدودیت · استقرار · نگهداری │
└───────────────▲───────────────────────────────────┬───────────────────┘
                │ SSH (نصب اولیه)                    │ HTTP + X-Titan-Token
                │                                   ▼
┌───────────────┴────────────────── نود (دیتاپلین) ─────────────────────┐
│  Nginx 443 (stream, ssl_preread)  →  Nginx 8443 (TLS، سایت پوششی، مسیرها) │
│                                    →  Xray inbounds (127.0.0.1:10000+)     │
│                                    →  Xray در حالت REALITY (passthrough)  │
│  Xray API 127.0.0.1:10085  ← آمار مصرف و کاربران آنلاین                    │
│  TiTaN Agent 62050         ← اعمال state، سلامت، لاگ، ACME، shaping        │
└────────────────────────────────────────────────────────────────────────┘
```

**اصل طراحی:** پنل هرگز در مسیر داده نیست. اگر پنل بخوابد، کاربران بدون هیچ قطعی به کار خود ادامه می‌دهند. این تفاوت اصلی با پنل‌هایی است که خودشان پروکسی می‌کنند.

---

## ۲) نقشه‌ی پورت‌ها روی نود

| پورت | پروتکل | مالک | توضیح |
|---|---|---|---|
| 22/tcp | SSH | سیستم | نصب اولیه و عیب‌یابی |
| 80/tcp | HTTP | Nginx | چالش ACME + ریدایرکت به HTTPS |
| 443/tcp | TCP | Nginx stream | نقطه‌ی ورود اصلی: مسیرهای HTTP + REALITY (با SNI) |
| 8443/tcp | TCP | Nginx http | vhost داخلی؛ **از اینترنت بسته است** و فقط از 443 قابل دسترسی است |
| 10000+/tcp | TCP | Xray | inboundهای محلی (loopback) و API آمار |
| 2053/2083/8443/… | TCP/UDP | Xray | inboundهای `direct` (TCP/QUIC/Hysteria2/WireGuard) |
| 62050/tcp | TCP | Agent | کنترل‌پلین، توکن‌محافظت‌شده |

چرا این تقسیم؟ چون REALITY باید دست‌نخورده به Xray برسد، مسیرهای HTTP باید TLS را در Nginx تمام کنند و پروتکل‌های خام باید پورت اختصاصی داشته باشند. Nginx stream با `ssl_preread` این تفکیک را روی همان ۴۴۳ انجام می‌دهد.

## ۳) جریان استقرار (Deployment flow)

```
تغییر در پنل (کاربر/کانفیگ/سهمیه)
        │
        ▼
Node.config_dirty = True            ← هیچ درخواستی به نود نمی‌رود
        │
        ▼ (worker «استقرار» هر ۳۰ ثانیه، یا دکمه‌ی دستی)
provisioner.preflight(node, inbounds)      ← قواعد: تداخل پورت، کلید REALITY، مسیر، گواهی
        │            خطا؟ → استقرار متوقف و پیام واضح به اپراتور
        ▼
build_desired_state()  → { xray_config, nginx_main, nginx_vhost, nginx_redirect,
                           sysctl, decoy_html, firewall_rules, [hy2_yaml], [wg_conf] }
        │
        ▼  POST /apply  (X-Titan-Token)
Agent: validate → backup → write → reload → health-check
        │            خطای اعتبارسنجی؟ → بازگردانی فایل‌های قبلی (rollback)
        ▼
گزارش نتیجه در ActivityLog و NodeTask
```

مزیت: یک تغییر اشتباه، هرگز یک نود اینترنتی را از دست نمی‌دهد؛ Xray و Nginx فقط پس از پاس شدن تست‌ها ری‌استارت می‌شوند.

## ۴) مدل داده (خلاصه)

| جدول | نقش |
|---|---|
| `admins` / `admin_sessions` | کارکنان پنل، نقش‌ها (owner/admin/reseller/viewer)، نشست‌ها |
| `nodes` | هر سرور: دامنه، کشور، وضعیت، متریک زنده، توکن ایجنت، اطلاعات SSH، فلگ‌ها |
| `inbounds` | هر سرویس پروتکل: پروتکل/ترابری/امنیت، پورت عمومی و داخلی، مسیر، SNI، ALPN، فینگرپرینت، کلیدهای REALITY |
| `users` | مشتری: حجم، مصرف، انقضا، حد IP، حد سرعت، چرخه‌ی ریست، توکن ساب |
| `clients` | اتصال یک کاربر به یک inbound + `email_tag` (همان tag مصرف در Xray) |
| `subscriptions` / `subscription_items` | گروه اشتراک با رمز اختیاری و لینک عمومی |
| `traffic_samples` / `node_samples` | باکت‌های ساعتی → نمودار و گزارش |
| `activity_logs` / `node_tasks` / `notifications` / `settings` | شفافیت عملیات و تنظیمات |

نکته‌ی کلیدی: `Client.email_tag` یکتا است (`{username}-{inbound_id}`) و همان چیزی است که در Xray با آن آمار مصرف می‌گیریم. پس آمار همیشه به یک کاربر و یک کانفیگ قابل نسبت دادن است.

## ۵) حسابداری ترافیک

1. ایجنت با `xray api statsquery` شمارنده‌های **تجمعی** هر کاربر را می‌خواند.
2. پنل آخرین مقدار هر `(node, email)` را در حافظه نگه می‌دارد و **دلتا** را محاسبه می‌کند.
3. دلتا در `traffic_samples` (ساعتی، per-user) و `node_samples` ذخیره می‌شود.
4. `enforce_quotas` هر دقیقه: انقضا، اتمام حجم، ریست دوره‌ای، و علامت‌گذاری نود برای استقرار مجدد.
5. ری‌استارت Xray باعث برگشت شمارنده می‌شود؛ منطق دلتا این حالت را تشخیص می‌دهد (اگر شمارنده کوچک‌تر شد، همان مقدار به‌عنوان دلتا در نظر گرفته می‌شود).

محدودیت IP: ایجنت از لاگ دسترسی (`Xray` + `proxy_protocol`) نگاشت «آی‌پی → ایمیل» می‌سازد؛ پنل تعداد آی‌پی‌های فعال هر کاربر را می‌شمارد و در حالت strict، کاربر متخلف را غیرفعال می‌کند.

---

## ۶) پرفورمنس (چرا سریع است)

**کرنل (ایجنت اعمال می‌کند):** `fq` + `bbr`، `tcp_fastopen=3`، `somaxconn=65535`، `tcp_slow_start_after_idle=0`، بافرهای ۶۴MB، `ip_local_port_range` گسترده، `file-max=1000000`.

**Nginx:** `worker_rlimit_nofile 65535`، `worker_connections 32768`، `epoll` + `multi_accept` + `reuseport`، `tcp_nopush/tcp_nodelay`، `open_file_cache`، `ssl_session_cache` 100MB، `ssl_early_data` (0-RTT)، `proxy_buffering off` و timeoutهای طولانی برای مسیرهای تونل.

**Xray:** `tcpcongestion: bbr`، `tcpFastOpen`، `tcpKeepAlive*`، `tcpNoDelay`، `bufferSize` سیاستی، `domainStrategy: UseIPv4v6`، sniffing بهینه، مسدودسازی `geoip/geosite:private` و تبلیغات و bittorrent.

**پنل:** SQLite در حالت WAL + جمع‌آوری موازی آمار همه‌ی نودها با `asyncio.gather`؛ داشبورد با یک درخواست JSON سبک هر ۱۵ ثانیه به‌روز می‌شود.

---

## ۷) امنیت

- رمزها با **Argon2id** هش می‌شوند؛ نشست‌ها در دیتابیس با انقضا و قابل ابطال هستند.
- توکن ایجنت به‌ازای هر نود یکتا است و در `X-Titan-Token` ارسال می‌شود؛ ایجنت فقط یک لیست سفید از دستورات (`/exec`) را می‌پذیرد.
- `PANEL_ALLOWED_IPS` اجازه‌ی ورود را به شبکه‌های مشخص محدود می‌کند.
- کانفیگ‌ها هرگز بدون `xray -test` روی سرور زنده اعمال نمی‌شوند.
- سایت پوششی روی ۸۴۳ پاسخ می‌دهد تا اسکنرها روی دامنه چیزی جز یک وب‌سرور معمولی نبینند.

---

## ۸) مسیر توسعه (پیشنهاد گام بعدی)

1. **ربات تلگرام** (مدیریت کانفیگ/کاربر + اعلان اتمام حجم) — زیرساخت `telegram_id` و اعلان‌ها آماده است.
2. **شاخه‌ی چندمستأجری (reseller)** با محدودیت حجم کل و کیف پول.
3. **کلاینت Forge/Amnezia** کنار Clash در صفحه‌ی اشتراک.
4. **Postgres** برای مقیاس چند‌هزار‌کاربره (فقط `DATABASE_URL` تغییر می‌کند).
5. **هشدارهای Prometheus** از `/api/dashboard` و متریک‌های ایجنت.
